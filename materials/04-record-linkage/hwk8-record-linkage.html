Linking Records

Organizations frequently maintain information about the same individuals that is collected from different sources.

Combining these databases provides a more complete picture of individuals, but identifying records that refer to the same person is challenging. Names may be misspelled, addresses may be incomplete, and dates of birth or other identifying information may be missing or incorrectly recorded.

In this assignment, you will investigate and compare results from a record-linkage procedure using the FEBRL 4 dataset. Your goal is to identify pairs of records that refer to the same individual, evaluate the quality of your linkage procedure, and investigate the consequences of different methodological choices.

Data

The FEBRL 4 dataset (available through the R package irelink) consists of two files:

  • febrl4a: 5,000 original records.
  • febrl4b: 5,000 corresponding duplicate records.

Each record contains information such as first and last name, street address, suburb, postcode, state, date of birth, and social security identifier.

The duplicate records contain deliberately introduced errors, including typographical errors, missing values, and transpositions.

Question 1: Getting an overview of the situation

Before attempting to link the records, familiarize yourself with the two databases. Answer the following questions and present appropriate tables and/or visualizations to support your observations.

  1. Report the number of observations and variables in each dataset.
  2. Describe the variables and their types.

  4. Which variable(s) appear to be particularly useful for record linkage? Explain your choice(s).
  5. Investigate the quality of the identifying information:

    • Which variables appear to have been corrupted?

Question 2: Set up an Evaluation Framework

  1. Construct a dataset AB of all possible index pairs between the two datasets using all combinations of the rec_id variables.

  2. Use the values on the two index variables to create a variable match_gt that contains the ground truth for matches, i.e. is TRUE if the pair of indices corresponds to a match and FALSE otherwise.

  3. Create a summary table of the match_gt variable and discuss.

Question 3: Exact Matching

  1. Identify pairs in the two data sets that agree exactly on:
    • Given name and surname.
    • Date of birth.
    • Postcode.
  2. Construct a linkage procedure that identifies pairs agreeing on all three criteria.
  3. Identify pairs that agree on the social security id.
  4. Evaluate the resulting matches from 2 and 3 in terms of the number of identified pairs, true matches, false matches, and missed matches.

Discuss why exact matching is unlikely to identify all true matches.

Question 4: String Comparisons and Similarity Measures

Exact matching is often too restrictive. For example, two records may contain the names “Katherine” and “Katharine”, or addresses may differ by a single character.

Investigate methods for comparing strings.

  1. Use the stringdist package to calculate string similarity measures for all pairs of given names, surnames, and addresses. Consider both Jaro-Winkler similarity and Levenshtein distance.
  2. Compare the similarity distributions for true matching and non-matching pairs. Is one similarity measure always ‘better’ (define!) than the other?
  3. What would be good thresholds for each of the variables?

Illustrate your findings with appropriate plots.

Question 5: Candidate Generation and Blocking

Comparing all possible pairs between two datasets of 5,000 records each requires 25 million comparisons.

To make record linkage more computationally efficient, blocking variables are used, i.e. only those records are compared that agree on selected characteristics. These records are called candidate pairs. Two important measures are considered when using blocking:

  • Pair completeness: proportion of true matches retained in the candidate set.
  • Reduction ratio: proportion of all possible pairs eliminated by blocking.
  1. Create candidate pairs for all records that agree on (a) birth year, (b) birth day (without the year), and (c) the first two letters of the surname.
  2. For each blocking strategy, report the number of candidate pairs.
  3. Calculate pair completeness and reduction ratio for each of the blocking strategies.
  4. Discuss the trade-off between computational efficiency and the risk of excluding true matches.

Question 6: Probabilistic Record Linkage with ireLink

The irelink package provides functions for specifying comparisons, blocking, estimating model parameters, and predicting matches. See below for instructions on how to use the package.

The overall goal of this question is to use the irelink package to fit and evaluate a record linkage model.

  1. Create a specification with il_spec that compares records between the two datasets using the insights from the previous questions. Explain your choices.

  2. Fit the model and predict match probabilities (use a threshold of 0.5 to start).

  3. Evaluate the identified pairs against ground truth.

The irelink website describes its functionality at the example of the febrl data.

An example specification is:

library(irelink)

spec <- il_spec() |>
  il_compare(given_name, cl_name()) |>
  il_compare(surname, cl_name()) |>
  il_compare(date_of_birth, cl_exact()) |>
  il_compare(postcode, cl_exact()) |>
  il_block_on(surname) |>
  il_block_on(given_name)

Fit a linkage model:

con <- DBI::dbConnect(duckdb::duckdb())

## duckdb is storing downloaded extensions and secrets under ~/.duckdb:
## ℹ /Users/hofmann/.duckdb
## This persists across sessions and is shared with the DuckDB CLI and other clients.
## ℹ Run duckdb(shared_home = FALSE) to use a temporary directory instead.

model <- il_model(
  febrl4a,
  febrl4b,
  spec = spec,
  con = con,
  link_type = "link"
)

Estimate model parameters (Note, that this is a pipeline that successively changes the model!):

model <- il_estimate_prior(
  model,
  block_on(given_name, surname),
  block_on(surname, suburb),
  recall = 0.6
)

model <- il_estimate_u(model, max_pairs = 1e5)

model <- il_estimate_em(model, block_on(surname))

## EM trained: given_name, date_of_birth, and postcode | skipped (blocked on):
## surname

model <- il_estimate_em(model, block_on(suburb))
